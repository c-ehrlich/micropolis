# codegen package overview

## Purpose
The `codegen/` package produces derived TypeScript sources and data tables that keep the game data model, routing, and localization in sync across the monorepo. It is intentionally small and script driven: each generator reads authoritative sources (types, fixtures, schema files, route definitions) and emits typed artifacts in other packages. The outputs are treated as build artifacts and are regenerated by `pnpm codegen`.

Key goals:
- Keep serialization formats stable and compact (actions/conditions).
- Provide strongly typed route and campaign name unions.
- Generate i18n lookup tables and translation maps from canonical game data.
- Provide a GraphQL schema import map in the full repo.

## Entry points and layout

- `codegen/generate-all.tsx`
  - Orchestrator. Loads all generator scripts (via dynamic `import(...)`).
- `codegen/generate-actions.tsx`
  - Generates action/condition encoding, decoding, and formatting code plus stable ID maps.
- `codegen/generate-campaign-names.tsx`
  - Generates a union type of campaign map slugs.
- `codegen/generate-graphql.tsx`
  - Generates a GraphQL schema import map.
- `codegen/generate-routes.tsx`
  - Generates route type unions and a top-level route name set.
- `codegen/generate-translations.tsx`
  - Generates i18n entity maps, campaign translations, and message system vocabularies.
- `codegen/lib/sign.tsx`
  - Adds a `/* @generated(<sha256>) */` header used to track content changes.
- `codegen/lib/traverse.tsx`
  - Babel traverse wrapper compatible with both CJS and ESM default exports.

All scripts are Node + TypeScript ESM, executed through `ts-node/esm` (see the shebangs) and formatted with Prettier. The package itself only depends on lightweight build-time libraries (Babel parser/traverse, glob, chalk, prettier, @nkzw/core helpers).

## How it interacts with the monorepo

High-level data flow:

1. `apollo/` defines the authoritative action, action response, and condition TypeScript types.
2. `codegen/generate-actions.tsx` reads those types and emits `apollo/EncodedActions.tsx`, `apollo/FormatActions.tsx`, and updates `apollo/ActionMap.json` + `apollo/ConditionMap.json`.
3. `hera/`, `hermes/`, and `i18n/` expose game content (maps, campaigns, entity info, message vocabularies) that `codegen/generate-translations.tsx` converts into translation tables used at runtime in `hera/` and `i18n/`.
4. `ares/` (closed-source app) defines client routes; `codegen/generate-routes.tsx` extracts them into `apollo/Routes.tsx`.
5. `artemis/` (closed-source server) contains GraphQL schema modules; `codegen/generate-graphql.tsx` builds an import map for those modules.
6. `hermes/` fixtures are scanned to create a stable campaign map name union via `generate-campaign-names.tsx`.

The scripts are written to degrade gracefully in the open-source repo. If closed-source files are missing, the generators warn instead of failing (controlled by `infra/isOpenSource.tsx`).

## Generator details

### 1) Actions, responses, and conditions
File: `codegen/generate-actions.tsx`

Inputs:
- TypeScript definitions:
  - `apollo/Action.tsx`
  - `apollo/ActionResponse.tsx`
  - `apollo/Condition.tsx`
  - `apollo/Objective.tsx`
  - `apollo/HiddenAction.tsx`
- Stable ID maps:
  - `apollo/ActionMap.json`
  - `apollo/ConditionMap.json`

Outputs:
- `apollo/EncodedActions.tsx` (data contract and encoder/decoder)
- `apollo/FormatActions.tsx` (human-friendly string formatting)
- Updated `apollo/ActionMap.json` and `apollo/ConditionMap.json`

Key data structures:
- Action/condition definitions are parsed from TypeScript type aliases with object literal types. Example expectation: a type named `MoveAction` must contain a `type: 'Move'` literal field.
- Each type is assigned a stable numeric ID (from `ActionMap.json` / `ConditionMap.json`).
- Properties are converted into a compact, positional tuple encoding (`EncodedAction` / `EncodedActionResponse` / `EncodedCondition`) to minimize payload size.

Type extraction rules (high-level):
- Allowed value kinds: number, string, boolean, string literal, reference types, arrays, nested objects, and entity maps (`ImmutableMap<Vector, Entity>`).
- Special reference handling:
  - `Vector` becomes two numbers (x, y) in the encoded tuple.
  - Entity maps become `PlainEntitiesList<PlainEntity>` via `encodeEntities` / `decodeEntities` from `athena`.
  - Scalars like `Biome`, `Crystal`, `PlayerID`, `Skill` are passed through as plain values (with `toX` casting on decode).
  - Custom encoders (e.g., `ChaosStars`, `DynamicPlayerID`, `Reward`, `Teams`, `Objective`) use specific `encodeX` / `decodeX` helpers.
- Optional properties are encoded as nullable tuple slots; trailing nulls are removed from the output to keep tuples short.

Stability guarantees and validation:
- The stable ID maps are treated as a schema registry. New types get a new ID; existing IDs never change.
- Property order is anchored to the stable maps. Adding a new non-optional property to an existing type is rejected (it would change the encoded tuple shape and break compatibility).
- Optional properties may be appended (or merged for action responses), enabling backward-compatible evolution.

Runtime artifacts:
- `EncodedActions.tsx` exports:
  - Encoded tuple types
  - `encodeAction(s)`, `encodeCondition(s)`, `encodeActionResponse(s)`
  - `decodeAction(s)`, `decodeCondition(s)`, `decodeActionResponse(s)`
  - `encodeActionID` / `decodeActionID` for stable action response IDs
- `FormatActions.tsx` exports:
  - `formatAction(s)` and `formatActionResponse(s)` for CLI/debug output
  - Custom formatting for vectors, entities, unit/building lookups, and attack directions

Why this matters for other languages:
- The encoded tuple format, stable numeric IDs, and property ordering are the interoperability contract. A reimplementation should treat `ActionMap.json` and `ConditionMap.json` as the canonical schema. The decoder/encoder logic is a pure structural transform and can be reproduced in any language once those tables and type definitions are known.

### 2) Campaign map name union
File: `codegen/generate-campaign-names.tsx`

Inputs:
- `hermes/map-fixtures/*.tsx`
- `fixtures/map/*.tsx`

Process:
- Dynamically imports map modules, filters those tagged with `metadata.tags` containing `campaign`.
- Slugifies the map names using `apollo/lib/toSlug.tsx`.
- Sorts and emits a string union type.

Output:
- `hermes/CampaignMapName.tsx` with `export type CampaignMapName = '...' | '...';`

### 3) GraphQL schema import map
File: `codegen/generate-graphql.tsx`

Inputs:
- `artemis/graphql/nodes/*.tsx`
- `artemis/graphql/mutations/*.tsx`

Process:
- Enumerates schema files, builds sorted `import './path'` statements.
- In OSS mode (no internal files), it warns if no files are found.

Output:
- `artemis/graphql/schemaImportMap.tsx`

### 4) Route type generation
File: `codegen/generate-routes.tsx`

Inputs:
- `ares/src/ui/Main.tsx` (React Router `Route` components)

Process:
- Parses JSX with Babel and extracts all `Route` elements and their `path` props.
- Validates that routes start with `/` and ignores wildcard `*`.
- Produces:
  - `Route`: top-level routes with parameter placeholders replaced by `${string}`.
  - `UserRoute`, `UserMapRoute`, `UserCampaignRoute`: derived from `/:username/...` subroutes.
  - `Route` constant set: top-level route names (used for validation or UI logic).
- When the `ares/` app is missing (OSS repo), it logs a warning instead of failing.

Output:
- `apollo/Routes.tsx`

### 5) Translation and message maps
File: `codegen/generate-translations.tsx`

Inputs:
- Map fixtures: `hermes/map-fixtures/*.tsx`, `fixtures/map/*.tsx`
- Campaign fixtures: `fixtures/campaign/*.tsx`
- Game entity catalogs (athena): `info/Building`, `info/Unit`, `info/Tile`, `info/Decorator`, `info/Weapon`, `info/MovementType`
- Message system data (athena): `message/Message.tsx`
- Campaign messaging (hermes): `messages/ActivatePowerMessages.tsx`, `unrollCampaign.tsx`

Process summary:
- Builds entity name lists (Buildings, Units, Tiles, etc.) and description lists with metadata for translators.
- Gathers map names from fixture metadata.
- Traverses campaign effects to extract character message strings, using `getMessageKey` to deduplicate.
- Replaces `{name}`-style placeholders with `fbt.param` references so translations keep name substitution behavior.
- In open-source mode, emits placeholder campaign metadata instead of internal campaign lists.

Outputs:
- `i18n/Entities.ts`
  - Default export map of unique entity/map names with translator hints.
- `hera/i18n/EntityMap.tsx`
  - Per-entity name and description maps (wrapped in `fbt`).
- `hera/i18n/CampaignMap.tsx`
  - Campaign name/description translation metadata and character message translations.
- `hera/i18n/MessageMap.tsx`
  - Translated message vocabulary, conjunctions, templates, and punctuation for the message system.

Why this matters for other languages:
- The translation pipeline is deterministic and data-driven. The key concepts to reproduce are:
  - Central catalogs for names and descriptions.
  - Stable message keys derived from message content and metadata.
  - Placeholder-aware translation templates for character names and message grammar.

## Behavioral notes and invariants

- All generated files are formatted by Prettier and signed with a sha256 header (via `sign.tsx`), making the generation deterministic and cache-friendly.
- Generators are allowed to warn instead of failing when running in open-source mode (`infra/isOpenSource.tsx`). This keeps the OSS repo functional without internal app/server sources.
- `generate-actions.tsx` is the most sensitive generator: it encodes the network/serialization contract for gameplay events. Any reimplementation must preserve the tuple order, optional rules, and stable numeric IDs.

## Recreating in another language

If you want to build a codegen package for another engine or language, treat `codegen/` as a thin layer that transforms TypeScript-level domain definitions into stable, language-agnostic artifacts:

- Build a schema registry for actions/conditions (equivalent to `ActionMap.json`/`ConditionMap.json`).
- Parse the authoritative type definitions (or a JSON schema equivalent) and emit:
  - Compact, positional encodings with a stable discriminant.
  - Corresponding decoders and formatters for debugging.
- Convert game content catalogs and fixtures into localization tables and message templates.
- Extract routing or schema information from the application layer to keep it in sync with shared libraries.

This design keeps the core gameplay model portable while letting different frontends/backends share stable contracts generated from a single source of truth.
