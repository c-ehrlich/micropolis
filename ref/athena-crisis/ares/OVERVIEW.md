# Ares Package Overview

## Status in this repo
- `ares/` is a placeholder in the open-source mirror. Only `package.json` is present; source code (e.g. `src/`, build config, and app entry points) is intentionally missing.
- The role and architecture below are inferred from `ares/package.json`, shared monorepo conventions, and public interfaces in other packages.

## Purpose (in the full monorepo)
Ares is the main **client application** for Athena Crisis. It is the app shell that:
- boots the game UI and orchestration layer,
- communicates with the backend (closed-source `artemis/`),
- wires platform services (web/PWA + native wrappers),
- handles payments, auth, telemetry, and real-time multiplayer,
- embeds the shared rendering/interaction engine from `hera/`.

In short: **Ares is the product-facing app that composes the open-source engine packages into a playable game**.

## Key interfaces and data structures Ares must integrate
These types live in open-source packages and define the boundary that Ares must honor.

### Actions and responses (Apollo)
- **Actions** are discriminated unions (e.g. `Move`, `AttackUnit`, `CreateUnit`, etc.) defined in `apollo/Action.tsx`.
- **Action responses** are also discriminated unions in `apollo/ActionResponse.tsx`.
- **Encoding/decoding** is handled by generated helpers (missing in OSS):
  - `apollo/EncodedActions.tsx` (generated by codegen in the full repo).
  - `ActionMap.json` provides stable IDs for wire format.

### Game state history (Apollo)
From `apollo/Types.tsx`:
- `GameState` is an array of `[ActionResponse, MapData]` pairs.
- `EncodedGameState` is an array of `[EncodedActionResponse, PlainMap]` pairs.
- `GameActionResponse` has the shape:
  - `self: { actionResponse, buildings?, units? } | null`
  - `others?: Array<{ actionResponse, buildings?, units? }>`
  - `message?: EncodedClientMapMessage | null`
  - `timeout?: number | null`
- `EncodedGameActionResponseWithError` is a union that includes:
  - the normal encoded response,
  - error/refresh/passthrough control codes (`{ n: 'x' }`, `{ n: 'r' }`, etc.),
  - a message payload (`{ n: 'm', message: ... }`).

### Turn-state snapshots (Hermes)
From `hermes/game/getTurnState.tsx`:
- `PreviousGameState` is a tuple:
  - `[state, lastActionResponse, effects, recentActions?]`
  - `state` is `MapData` or `PlainMap` (encoded form).
  - `recentActions` holds per-turn action history.
- `encodeTurnState` / `decodeTurnState` convert to/from encoded forms for storage or transport.

### Real-time socket protocol (Apollo)
From `apollo/socket/Types.tsx`:
- Client events:
  - `/game/action` emits `(currentGameID, EncodedAction, callback)`.
  - `/game/spectate` and campaign/pending-game events for spectators.
- Server events:
  - `/game/action` emits `(gameID, EncodedGameActionResponseWithError)`.
  - campaign and pending-game update events.
From `apollo/socket/Room.tsx`:
- Helper functions to compute room names:
  - `gameRoom(gameId)` -> `/game/<id>`
  - `pendingGameRoom(pendingGameId)` -> `/pending-game/<id>`

### Routes (Apollo)
From `apollo/routes/*`:
- Typed route builders for user, map, and campaign URLs:
  - `getCampaignRoute(slug, route?)` -> `/${slug}` or `/${slug}/${route}`
  - `getMapRoute(slug, route?)` -> `/${slug}` or `/${slug}/${route}`
  - `getUserRoute(username, route?)` -> `/u/${username}` or `/u/${username}/${route}`
These depend on generated `apollo/Routes.tsx` (missing in OSS mirror).

## Expected data flow in Ares (inferred)
This is the minimal orchestration Ares must provide to make the engine playable.

1) **Bootstrapping**
   - Initialize Relay environment (GraphQL).
   - Fetch user profile, game metadata, campaign state, and initial map snapshots.
   - Decode maps into `MapData` (`athena`) and game history into `GameState` (`apollo`).

2) **Render loop**
   - Pass `MapData`, `Effects`, and `ActionResponse` history to `hera` components for rendering.
   - Use `ui/` primitives for app chrome (menus, dialogs, settings).

3) **User actions**
   - Interaction in `hera` yields `Action` objects (`apollo`).
   - Ares encodes actions (`EncodedAction`) and sends them to the server:
     - via Relay mutation, or
     - via socket `/game/action` for real-time matches.

4) **Server responses**
   - Decode `EncodedGameActionResponseWithError`.
   - Apply `ActionResponse` updates to `MapData` (via Apollo action application).
   - Update UI state and turn snapshots (`hermes`).

5) **Persistence / replay / undo**
   - Encode `GameState` and `PreviousGameState` for storage.
   - Restore using `decodeGameState` / `decodeTurnState`.
   - Use these artifacts for reconnect, replay, or fast-forward.

6) **Live updates**
   - Subscribe to `socket.io` rooms (`gameRoom`, `pendingGameRoom`).
   - React to `/campaign-state/update` and `/pending-game/update` to refresh UI.

## Re-creating Ares in another language (architecture checklist)
To replicate Ares in another codebase, you would need to implement the following system modules:
- **App shell**: routing, screens, navigation, settings, auth.
- **Data layer**: GraphQL or equivalent for fetching persistent entities (users, games, campaigns).
- **Real-time layer**: socket protocol matching `apollo/socket` events.
- **Game orchestration**: encode/decode action pipeline and deterministic state updates.
- **Rendering integration**: a presentation layer that consumes `MapData` + effects + action history.
- **Persistence**: local storage for `GameState` and `PreviousGameState`.
- **Platform services**: PWA caching, native wrappers, push notifications, IAP, payments.
- **Telemetry & crash reporting**: error boundaries + reporting.

The tightest contracts to preserve are:
- `EncodedAction` / `EncodedActionResponse` formats (for server interoperability).
- `GameState` / `PreviousGameState` tuples (for replay, undo, and turn summaries).
- Socket event names and payload signatures (for real-time multiplayer).
